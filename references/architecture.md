# 三层审改架构规范

本文档定义多轮语言审改中的线程职责划分、四类专职审核工序及工作区文件通信协议。

---

## 一、 线程职责划分

系统包含三类线程，由宿主环境（Harness）的子智能体机制管理生命周期：

### 1. 顶层调度者（Orchestrator，主线程）
负责初始化 `.polish_workspace/` 通信目录、调用静态扫描与文本提取脚本、按序派发专职审核子线程、唤醒常驻撰改者，并检查轮次输出以判定工序切换或终止。顶层调度者不读取指导书、不查阅代码、不直接改写报告，确保上下文轻量。

### 2. 常驻撰改者（Writer-Refiner，单一持久子线程）
负责初稿撰写及后续全部轮次的文稿修改（可直接维护 `.docx` 或 `.md` 文稿）。顶层调度者在首轮创建该子线程，记录其会话标识（`conversationId`），后续轮次始终复用同一会话。

写稿、改稿合一旨在保持实验事实连续性：审改中的大量批注要求增补代码模板行号、主函数调用或底层硬件机理（见 [classic_critiques.md](classic_critiques.md) 案例一、案例七）。写稿线程已掌握源码及原始日志，能准确增补上述细节，并在审核意见违背专业事实时行使反驳权（案例八）。

### 3. 专职审核者（Specialist Reviewers，每轮新建子线程）
单一审核线程若同时检查 14 类问题，极易分散注意力。因此审核职责按工序拆分为四类专职角色（指令见 [reviewer_prompt.md](reviewer_prompt.md)）。每次审查均创建全新的子线程，仅负责所属工序的 2～5 类错误，输出批注后即销毁。

---

## 二、 四道专职审核工序

顶层调度者按“先定大框架、再删废话、后补逻辑、最后抠字句”的顺序推进四道工序。前一道工序输出通过标记后，方进入下一道工序：

### 1. 工序一：宏观结构审核（第 1、2、3 类错误）
- **职责范围**：仅对照任务要求审查章节增删与标题，不评价具体字词。
- **负责类别**：1. 冗余的非核心过程描述；2. 脱离代码修改行为的原理概述；3. 双中心并列标题。
- **通过标志**：输出 `STAGE_1_PASSED`，锁定章节结构。

### 2. 工序二：信息冗余审核（第 4、5、6、8、9 类错误）
- **职责范围**：专职“做减法”，识别并删除动摇论点或无信息增益的冗余语句。
- **负责类别**：4. 防御性局限声明；5. 无信息增益的自我证实表述；6. 面向专业阅读者的基础常识解释；8. 重复图表已有信息；9. 冗余的图表引导。
- **通过标志**：输出 `STAGE_2A_PASSED`。

### 3. 工序三：段落逻辑审核（第 10、12 类错误）
- **职责范围**：专职“理逻辑、补机理”，对照 [classic_critiques.md](classic_critiques.md) 剖析自然段内各句关系，扩充底层归因。
- **负责类别**：10. 空洞归因；12. 句间逻辑断层。
- **通过标志**：输出 `STAGE_2B_PASSED`。

### 4. 工序四：句法词法审核（第 7、11、13、14 类错误）
- **职责范围**：专职“抠字句”，结合 [check_prose.py](../scripts/check_prose.py) 静态扫描线索，打磨全文（含工序三新扩写的段落）的词法与句法。
- **负责类别**：7. 人工智能过拟合词汇；11. 主语使用异常；13. 超长单句；14. 自然语言算术。
- **通过标志**：输出 `STAGE_2C_PASSED`，全流程终止。

## 三、 工作区文件通信协议

### 1. 通信文件定义
由于最终交付物通常为 `.docx` 文档，审核子线程无法用纯文本工具直接读取，顶层调度者在每轮派发审核线程前，运行 [check_prose.py](../scripts/check_prose.py)，同步生成纯文本镜像与静态扫描报告：
```bash
python scripts/check_prose.py <当前文稿.docx> --extract .polish_workspace/draft_view.md > .polish_workspace/prose_scan.txt
```
`.polish_workspace/` 下的固定通信文件如下：
- `task_spec.md`：任务要求或实验指导书。
- `draft_view.md`：由脚本从 `.docx`（或 `.md`）提取的纯文本镜像，每个正文段落标记为 `[P{n}]`，数据表格单元格标记为 `[T{t}R{r}C{c}]`，1×1 代码框标记为 `[1x1 代码/终端输出框]`（审核者只读）。
- `prose_scan.txt`：静态扫描输出，定位编号同 `draft_view.md` 对齐（审核者只读）。
- `round_{k}_review.md`：第 $k$ 轮批注单（审核者写入，撰改者只读）。
- `dispute_ledger.md`：批注处理记录与争议计数账本（撰改者维护，对审核者隐藏）。

### 2. 批注字段结构
`round_{k}_review.md` 中的每条批注包含四个字段：
- **定位原文**：注明位置编号（如 `[P35]` 或 `[T5R1C2]`）并精确摘录原句。
- **错误名称**：对应当前工序负责的标准错误名称。
- **原因说明**：客观分析该处表述为何削弱论点、造成冗余或导致逻辑割裂。
- **修改建议**：给出具体的删减、拆分或重写方向。

### 3. 撰改者响应状态
常驻撰改者在修改原 `.docx`（或 `.md`）文稿后，于 `dispute_ledger.md` 中登记响应状态：
- `ACCEPTED`：认可原因说明，已在原文稿中完成修改。
- `DISPUTED`：采纳建议会导致技术事实错误，或导致文本退回早期错误状态。须附上客观技术依据。

### 4. 二次争议搁置机制
同一位置在第 $k$ 轮被标记为 `DISPUTED` 后，若后续轮次的新审核者再次对该处提出异议，且撰改者仍认为不应修改（往返分歧达 2 次），立即在账本中升级为 `HOLD_FOR_HUMAN`，冻结该处文本，交由人工裁决。
