# 三层审改架构规范

本文档定义多轮语言审改中的线程职责划分、五道专职审核工序，以及工作区文件通信协议。

---

## 一、 线程职责划分

系统包含三类线程，由宿主环境（Harness）的子智能体机制管理生命周期：

### 1. 顶层调度者（Orchestrator，主线程）
负责前置检查实验材料是否齐全（若缺失代码或指导书则主动暂停并向用户索取）、初始化 `.polish_workspace/` 通信目录、派发专职审核子线程、唤醒常驻撰改者，并检查轮次输出以判定工序切换或终止。顶层调度者不在自身上下文中直接载入大篇幅报告正文，确保上下文轻量。

### 2. 常驻撰改者（Writer-Refiner，单一持久子线程）
负责初稿撰写及后续全部轮次的文稿修改（可直接维护 `.docx` 或 `.md` 文稿）。顶层调度者在首轮创建该子线程，记录其会话标识（`conversationId`），后续轮次始终复用同一会话。

写稿、改稿合一旨在保持实验事实连续性：审改中的大量批注要求增补代码模板行号、主函数调用或底层硬件机理（见 [classic_critiques.md](classic_critiques.md) 案例一、案例七）。写稿线程已掌握源码及原始日志，能准确增补上述细节，并在审核意见违背专业事实时行使反驳权（案例八）。

### 3. 专职审核者（Specialist Reviewers，每轮新建子线程）
单一审核线程若同时检查 15 类问题，极易分散注意力。因此审核职责按工序拆分为五类专职分身（各分身独立子手册与指令见 [reviewer_prompt.md](reviewer_prompt.md)），并与 `scripts/` 下的五个专项扫描模块一一配对。每次审查均创建全新的子线程，仅接收当前分身专属的扫描线索，输出批注后即销毁。

---

## 二、 五道专职审核工序

顶层调度者按“先定大框架、再删废话、后补逻辑、最后抠字句”的顺序推进五道工序。每道工序仅运行其对应的扫描脚本，且仅阅读该工序对应的独立错误子手册（详见 [error_taxonomy.md](error_taxonomy.md) 总谱索引），避免跨工序线索与庞大规则集干扰审核者注意力：

### 1. 工序一：宏观结构审核（第 1～3 类错误）
- **输入前置**：必须直读实验指导书原始裸文件（`{spec_path}`），避免二次转述遗漏必选实验模块与图表细节。
- **独立子手册**：[taxonomy_stage1_structure.md](taxonomy_stage1_structure.md)
- **配对脚本**：[scan_structure.py](../scripts/scan_structure.py)（输出全文章节标题树、双中心并列标题嫌疑、硬件环境与常规校验段嫌疑）。
- **负责类别**：1. 冗余的非核心过程描述；2. 脱离代码修改行为的原理概述；3. 双中心并列标题。
- **通过标志**：输出 `STAGE_1_PASSED`，锁定章节结构。

### 2. 工序二：信息冗余审核（第 4～6 类错误）
- **独立子手册**：[taxonomy_stage2_redundancy.md](taxonomy_stage2_redundancy.md)
- **配对脚本**：[scan_redundancy.py](../scripts/scan_redundancy.py)（输出防御性声明、自我证实表述、常识解释及段末防御性表达）。
- **负责类别**：4. 防御性局限声明；5. 无信息增益的自我证实表述；6. 面向专业阅读者的基础常识解释。
- **通过标志**：输出 `STAGE_2A_PASSED`。

### 3. 工序三：段落逻辑审核（第 9～10 类错误）
- **独立子手册**：[taxonomy_stage3_logic.md](taxonomy_stage3_logic.md)
- **配对脚本**：[scan_logic.py](../scripts/scan_logic.py)（输出空洞归因句式嫌疑、多句无显式过渡词的孤立陈述段线索）。
- **负责类别**：9. 空洞归因；10. 句间逻辑断层。
- **通过标志**：输出 `STAGE_2B_PASSED`。

### 4. 工序四：句法词法审核（第 11～15 类错误）
- **独立子手册**：[taxonomy_stage4_syntax.md](taxonomy_stage4_syntax.md)
- **配对脚本**：[scan_syntax.py](../scripts/scan_syntax.py)（输出 AI 过拟合词汇、伪拟人主语、同段高频重复词、超过15阅读单位的分句、自然语言算术线索、复合分支未拆分长段落线索）。
- **负责类别**：11. 人工智能过拟合词汇；12. 主语使用异常；13. 超长单句；14. 自然语言算术；15. 复合分支未拆分长段落。
- **通过标志**：输出 `STAGE_2C_PASSED`，进入图文审核。

---

### 5. 工序五：图文重复审核（第7～8类）
- 图文专职审核者负责第7～8类。
- 运行 `check_prose.py <文稿> --stage visuals --visual-assets .polish_workspace/visual_assets`。
- 输入当前任务要求、最新文稿、实际图片及图题、表格和相邻正文；图片完成后才结束本工序。
- 专属手册：[taxonomy_stage5_visuals.md](taxonomy_stage5_visuals.md)，配对脚本：[scan_visuals.py](../scripts/scan_visuals.py)。
- 通过标记 `STAGE_5_PASSED`，纯文字无图表且无占位符时为 `STAGE_5_SKIPPED`。材料未齐返回 `MATERIALS_PENDING`，补齐后重新审核。
- 五类职责固定，每道工序同一轮仅一个审核线程。图文审核修改正文后，重查受影响的冗余、逻辑和句长。

## 三、 工作区文件通信协议

### 1. 通信文件定义
由于最终交付物通常为 `.docx` 文档，审核子线程无法用纯文本工具直接读取，顶层调度者在每轮派发审核线程前，运行 [check_prose.py](../scripts/check_prose.py)（底层调用 [doc_parser.py](../scripts/doc_parser.py)），同步生成纯文本镜像与当前工序专属扫描报告：
```bash
python scripts/check_prose.py <当前文稿.docx> --extract .polish_workspace/draft_view.md --stage <当前工序> > .polish_workspace/prose_scan.txt
```
`.polish_workspace/` 下的固定通信文件如下：
- `task_spec.md`：任务要求或实验指导书。
- `draft_view.md`：由 [doc_parser.py](../scripts/doc_parser.py) 提取的纯文本镜像，正文段落标记为 `[P{n}]`，数据表格单元格标记为 `[T{t}R{r}C{c}]`，实际图片另由 `scan_visuals.py` 导出供查看；1×1 代码框标记为 `[1x1 代码/终端输出框]`（审核者只读）。
- `prose_scan.txt`：当前工序专属的静态扫描输出，定位编号与 `draft_view.md` 保持一致（审核者只读）。
- `review_stage{S}_r{R}.md`：工序 `{S}` 第 `{R}` 轮审查批注单（审核者写入，撰改者只读；例如首轮为 `review_stage1_r1.md`，若工序二驳回重改第二轮为 `review_stage2_r2.md`）。
- `dispute_log.md`：批注处理记录与争议跟踪（撰改者维护，对审核者隐藏）。

### 2. 批注字段结构
`review_stage{S}_r{R}.md` 中的每条批注包含四个字段：
- **定位原文**：注明位置编号（如 `[P35]` 或 `[T5R1C2]`）并精确摘录原句。
- **错误名称**：对应当前工序负责的标准错误名称。
- **原因说明**：客观分析该处表述为何削弱论点、造成冗余或导致逻辑割裂。
- **修改建议**：给出具体的删减、拆分或重写方向。

### 3. 撰改者响应状态
常驻撰改者在修改原 `.docx`（或 `.md`）文稿后，于 `dispute_log.md` 中登记响应状态：
- `ACCEPTED`：认可原因说明，已在原文稿中完成修改。
- `DISPUTED`：采纳建议会导致技术事实错误，或导致文本退回早期错误状态。须附上客观技术依据。

### 4. 争议冻结
1. **升级与冻结**：同一位置在第 $k$ 轮被标记为 `DISPUTED` 后，若后续轮次的新审核者再次对该处提出异议，且撰改者仍认为不应修改（往返分歧达 2 次），立即在 `dispute_log.md` 中升级为 `HOLD_FOR_HUMAN`，冻结该处文本，并在完成回复中将该位置通报给顶层调度者。
2. **调度者维护与注入**：顶层调度者统一维护【已冻结的人工裁决位置清单】。每当收到新增的 `HOLD_FOR_HUMAN` 项，即将其加入清单，并在派发后续审核子线程指令时，显式传入该冻结清单。
3. **审核者跳过**：专职审核者接收到冻结清单后，严格跳过对这些位置的审查与批注，仅审核文稿中其余未冻结文本。
4. **收敛与最终裁决**：当未冻结文本全部达标时，审核者正常输出 `STAGE_{S}_PASSED`，避免陷入往返死循环。全部工序结束后，若存在冻结位置，顶层调度者统一将所有待裁决项整理为条目清单，在对话中交由人类用户做最终裁断。
