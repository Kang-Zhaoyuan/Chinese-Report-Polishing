# 工序四审核规范：句法词法（第 11～15 类）

> 本手册仅供【句法词法审核者】使用，专注于词汇去 AI 化、主语校正、超长单句切分、自然语言算式公式化，以及收尾阶段的复合长段落切分。

### 11. 人工智能过拟合词汇

#### 症状定义
行文中使用了语言模型在英文翻译语料、软件测试语料或商业公文语料上过拟合的词汇，不符合中文科技报告平实、自然的母语书写习惯。

#### 严禁词汇清单
1. **软件工程测试行话迁移词**：
   - `基线`、`唯一基线`（指代优化前的原程序或参考实现时，应改为`原程序`、`优化前`或`基础版本`）
   - `探针`、`快照`、`证据`、`证据链`、`门禁`、`夹具`、`冒烟`、`烟测`、`可追溯`、`可追溯备份`、`最小改动`、`全量`、`dry-run`、`实测`、`验收矩阵`、`校验哈希值`、`兜底`、`对齐`、`收口`、`口径`、`透传`、`落盘`
   - *典型反例句*：“你说得对，但我将要开始探针、快照、证据、门禁、夹具，还有哈希、冒烟、基线了。我要先建立唯一基线，再进行可追溯备份，先进行最小改动，我先进行一轮烟测，检查114个门禁是否通过，上线前进行一轮全量dry-run，上线后校验哈希值，最后进行一轮实测的验收矩阵。”
2. **欧化翻译腔句式**：
   - `基于……而言`、`在……的背景下`、`不仅……而且……`、`一方面……另一方面……`、`通过采用一种基于……的……`
3. **绝对化修饰词**：
   - `极限`、`显著提升`（应改为`明显提升`或直接陈述具体数值）、`至关重要`、`深远影响`、`极其复杂`、`不容忽视`、`前所未有`
4. **商业公文套话词汇**：
   - `赋能`、`助力`、`打造`、`闭环`、`抓手`、`沉淀`、`协同`、`重塑`、`解构`、`升华`
5. **机械过渡套话**：
   - `你说得对`、`诚然`、`综上所述`、`总而言之`、`由此可见`、`值得注意的是`、`不可否认的是`、`显而易见`、`不难发现`
6. **空洞的“{形容词}性”伪学术评价套话**：
   - 包含以“性”字结尾的形容词名词化套话：如`鲁棒性`、`健壮性`、`灵活性`、`可扩展性`、`优越性`、`先进性`、`便捷性`、`易用性`、`全面性`、`科学性`、`规范性`、`严密性`、`适应性`、`通用性`等。
   - *白名单与边界*：`性能`、`性质`等具体科技实体名词属于合法词汇，予以豁免不作检查；正规技术专业术语（如`空间局部性`、`时间局部性`、`非线性`）可予保留。
   - *排查要求*：理工科实验报告中，“性”字绝大多数是形容词名词化的属性抽象词。若缺少具体的物理机制、硬件参数、算法复杂度或测试数据支撑，仅凭空声称“提高了灵活性”、“保证了健壮性”，均为典型 AI 假大空公文套话。静态扫描脚本已内置“性”字单字独立扫描清单（自动排除“性能”、“性质”），供审核者逐条核实裁决。
   - *典型反例句*：“从而极大地提升了系统的灵活性与可扩展性，保证了算法的鲁棒性与科学性。”（必须替换为具体的技术机制或直接删除）。

#### 原因说明
上述词汇是模型在特定语料上过拟合的产物，带有明显的机器生成痕迹，不符合中文母语者在技术报告中的表达习惯。应当将其全部替换为具体的技术动作，或替换为平实的中文词汇。

### 12. 主语使用异常

#### 症状定义
检查以下表达问题：
1. **非人主语缺失**：句子的动作由程序、线程、矩阵等客观对象发出，却省略了主语，直接以动词开头；
2. **伪拟人主语**：句子的动作实际上由人类作者做出（如选择优化对象），为规避第一人称“我”，将无生命的名词（如“实验”）写为主动施事主语；
3. **同段主语或介词高频重复**：为补齐主语，在同一自然段内，连续多个句子反复使用同一个主语词（如“程序”）或介词结构（如“在……中”）、修饰词（如“平均”）。

4. **指令动作后置**：操作步骤把动作放在对象后面，写成名词化短语。

#### 原因说明
实验报告严禁出现第一人称“我”，中文语法要求根据施事者属性正确处理主语：
1. 若动作的执行者并非人类（而是代码、程序、线程或矩阵），必须显式写出该客观主语，消除无主语悬垂句；
2. 若动作本身是人类做出的主观决策（如“选择该函数作为优化对象”），由于“实验”本身不能主动做出选择，强加主语“实验”会造成拟人化语病，此时应当直接省略主语；
3. 当补齐客观主语后，若同一自然段内出现 3 次以上相同的“程序”、“在”或“平均”，会造成行文呆板，应在顺承分句中适度省略后续重复词。

书写操作步骤和任务指令时，优先使用“动词＋对象”，保持原意及专业术语。

### 13. 超长单句

运行句长脚本，将超限项交由撰改者压缩、替换措辞或拆开动作。保存改写前副本，用 `python scripts/check_prose.py <文稿> --stage syntax --check --compare-to <副本>` 复检。仅添加逗号或空白的改写退回处理。

无法继续压缩时，在 `dispute_log.md` 记录原句、尝试和理由，交审核者确认 `LENGTH_EXCEPTION`。

### 14. 自然语言算术

#### 症状定义
使用中文文字描述算术运算（如“1000 除以 32 余 8”、“加速比取优化版速度除以原版速度”），或在前文已定义数学符号（如矩阵边长 $N$、块边长 $T$）的情况下，后文仍反复使用中文汉字描述参数取值。

#### 原因说明
对于已定义符号的物理量与算式，相比于自然语言汉字描述，专业数学公式表达更加精准、紧凑，符合理工科阅读者的符号直觉。

#### 典例 1：将汉字整除余数描述转化为算式
- **场景**：分析矩阵边长 1000 除以块边长 32 的余数关系。
- **修改前（反例）**：
  > 线程块边长为 32 时，矩阵边长从 256 增至 512. 乘加运算规模增大，运行时间从 1.555 ms 增至 12.796 ms. 同一块大小下，矩阵边长为 1000 时，耗时为 108.578 ms. 边长为 1024 时，耗时为 97.508 ms. 可能的因素是边界线程与访存排列. 1000 除以 32 余 8，因此最后一个块的每个边界方向只有 8 个有效位置. 这些边界块中的部分线程需要经过判断后退出. 1024 能被 32 整除，各线程块均覆盖完整区域. 两种行宽也会改变矩阵元素在内存中的排列，从而影响访问效率.
- **修改后（正例）**：
  > 线程块边长为 32 时，矩阵边长从 256 增至 512. 随着乘加运算规模增大，运行时间从 1.555 ms 增至 12.796 ms. 同一块大小下，矩阵边长为 1000 时，耗时为 108.578 ms；边长为 1024 时，耗时为 97.508 ms.
  >
  > 这一差异可能与边界线程和访存排列有关：由于 1000 = 32 × 31 + 8，最后一个块在每个边界方向只有 8 个有效位置. 这些边界块中的部分线程经过判断后退出. 相比之下，1024 能被 32 整除，各线程块均覆盖完整区域. 两种行宽也会改变矩阵元素在内存中的排列，从而影响访问效率.

### 15. 复合分支未拆分（Collapsed Enumeration Paragraph）

#### 症状定义
自然段排版折行达到 6 行以上（或字数超过 220 字符），且段内连续包含 2 项或以上自闭合的复杂逻辑分支（包含“第一/第二/第三”、“阶段一/阶段二/阶段三”等明显序列标记），将总述引导句、多个复杂分支及逆向对比强行压缩在单个没有物理换行的实体段落中，形成实心文本墙。

#### 原因说明
理工科实验报告中，每个复杂操作分支都包含完整的“条件-动作-状态”论述。若挤在一整段内，分号与序数词会淹没在密集的字行中，阅读者极难扫视定位。将各分支提升为独立自然段后，能利用中文版面天然的首行缩进（2 字符）在左侧形成凹凸视觉阶梯（Visual Anchors），使逻辑结构一目了然。

本规则执行时遵循以下柔性分寸，严禁机械教条：
1. **弹性标点**：总述句与各分支段末尾的标点（冒号、分号或句号）不作死板硬性规定，由撰改者依语境自然定夺；
2. **疏密相间**：全文允许保留 1 个左右紧凑致密的大段落（如操作步骤简单、全段 5 行以内的紧凑段），避免全篇逢分支必切导致的琐碎感。

#### 典例：拆分双向链表操作的三分支长段落
- **场景**：操作系统内核缓冲区管理实验中，说明原版磁盘缓存 `bcache` 双向循环链表同时保留 `prev` 与 `next` 指针的原因，涉及三类复杂链表操作。
- **修改前（反例：长达 11 行的单段复合分支实心文本墙）**：
  > 原版 bcache 将全部 struct buf 结点，组织为以 bcache.head 为哨兵的双向循环链表，并按 LRU 顺序排列，其中 head.next 指向最近使用块，head.prev 指向最久未使用块. 同时保留 prev 与 next 可支持三类链表操作：第一，当 bget() 检查目标块是否命中时，内核从 head.next 出发，沿 next 指针正向扫描链表；第二，当 bget() 未命中而需回收空闲块时，内核从 head.prev 出发，沿 prev 指针反向扫描，直接从尾端定位满足 refcnt = 0 的候选块；第三，当 brelse() 将引用计数减至 0 时，内核利用 b->prev 与 b->next 直接修改相邻结点指针，在 O(1) 时间内将 b 从原位置摘除，并头插至 head.next. 相比之下，若仅保留单向指针，反向查找尾端块或摘除中间结点，均需从表头额外遍历以定位前驱结点.
- **修改后（正例：总述引导句 + 3 个具有缩进阶梯的独立自然段）**：
  > 原版 bcache 将全部 struct buf 结点，组织为以 bcache.head 为哨兵的双向循环链表，并按 LRU 顺序排列，其中 head.next 指向最近使用块，head.prev 指向最久未使用块. 同时保留 prev 与 next 可支持三类链表操作：
  >
  > 第一，当 bget() 检查目标块是否命中时，内核从 head.next 出发，沿 next 指针正向扫描链表；
  >
  > 第二，当 bget() 未命中而需回收空闲块时，内核从 head.prev 出发，沿 prev 指针反向扫描，直接从尾端定位满足 refcnt = 0 的候选块；
  >
  > 第三，当 brelse() 将引用计数减至 0 时，内核利用 b->prev 与 b->next 直接修改相邻结点指针，在 O(1) 时间内将 b 从原位置摘除，并头插至 head.next. 相比之下，若仅保留单向指针，反向查找尾端块或摘除中间结点，均需从表头额外遍历以定位前驱结点.
